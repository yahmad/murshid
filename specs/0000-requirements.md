## 1. Functional Requirements

### (a) Phase 1: CLI MVP (v0.1)

#### Watcher and Compiler Integration
*   **REQ-F-101:** The tool MUST watch the developer's cargo workspace directory recursively, excluding `target/`, `.git/` folders (including any nested `.git/` subdirectories inside `.murshid_experiments/`), `.murshid_experiments/` itself, configuration directories (e.g. `.cargo/`), and any paths matching user-defined glob exclusion patterns specified under `watcher.exclude` in `config.toml`. Glob exclusion matching MUST evaluate against the canonical, symlink-resolved absolute paths of all monitored filesystem paths to prevent symbolic link directory bypasses. The watcher MUST ignore filesystem events for any files resolving outside the project workspace root, unless the external target path is explicitly declared in `config.toml` under `watcher.include_external_links`. If watcher initialization fails due to file handle limit exhaustion (`EMFILE` or `ENOSPC` errors), the application MUST automatically fall back to background directory polling (debounced at 2500ms) and log a system limit configuration warning to standard error.
*   **REQ-F-102:** The tool MUST use a filesystem watcher event loop (debounced by a configurable duration, defaulting to 1500 milliseconds) to detect changes in `.rs` files.
*   **REQ-F-103:** When a compilation trigger occurs, the tool MUST execute `cargo check --message-format=json` in an asynchronous background subprocess. The watcher daemon MUST enforce a workspace-wide build queue or mutex lock to serialize all compiler check subprocess executions, canceling any running processes and ensuring only a single check run executes at any time. To prevent cargo lock conflicts during concurrent build requests, the daemon MUST acquire a lock using cross-platform file locking APIs (e.g. `fs4` file locks) on the custom target directories. If a previous compiler check subprocess is actively running when a new compilation is triggered, the watcher MUST terminate it immediately (via standard `SIGTERM`, followed by `SIGKILL` after a 500ms grace period) before launching the serialized new run. To prevent lock conflicts and directory sharing collisions, the subprocess MUST be executed with the environment variable `CARGO_TARGET_DIR` set to a dedicated subdirectory: `<project-root>/target/murshid/`.
*   **REQ-F-104:** The parser MUST intercept the compiler's JSON output stream and extract:
    *   The primary compiler error code (e.g. `E0382`, `E0507`).
    *   The file path, starting/ending line and column numbers.
    *   The specific line content where the error occurred.
    *   The raw diagnostic explanation message.
*   **REQ-F-113:** Rate-Limiting Errors: The watcher MUST limit Socratic processing to a maximum of 3 errors per compile run, prioritizing errors in the active file.

#### Socratic Orchestration and Prompt Filtering
*   **REQ-F-105:** The tool MUST determine user mastery level by querying the local SQLite profile database prior to prompt generation.
*   **REQ-F-106:** Socratic Prompting: The LLM instructions MUST enforce conceptual analogies, progressive guidance, the total withholding of corrected code solutions, and the strict decoupling of worked example problem domains (e.g. using generic structures like standard library vectors or string slices rather than mirroring the user's proprietary project logic structure).
*   **REQ-F-107:** AST Output Filter: The local parser MUST filter any markdown code blocks returned by the provider. If the code block contains structures or signatures matching the user's active file, it MUST replace the block with an educational redaction notice.
*   **REQ-F-108:** The system MUST support pluggable BYOK providers (Gemini, Claude, and local Ollama) configurable via the local platform configuration file path.
*   **REQ-F-111:** Opt-in Feedback Loop: The tool MUST support the `murshid feedback` command to securely package, anonymize, and upload compiler diagnostics and session interaction traces (excluding source code) for product dogfood validation. Payload data MUST be encrypted end-to-end client-side using Thabit's bundled public key (RSA-4096 or equivalent) before transmission, and uploaded via HTTPS POST with a strict 3000ms connection timeout limit. The CLI MUST display the raw, unencrypted JSON payload to the user and prompt with an interactive confirmation check (`[y/N]`) before conducting encryption and transmission.
*   **REQ-F-112:** One-Click Setup Command: The tool MUST support the `murshid setup` interactive prompt command to configure API endpoints, platform credentials, and local directories. The command MUST support a `--silent` flag to run without user interaction, using defaults and auto-discovered tools.
*   **REQ-F-123:** Silent License Registration: The tool MUST support registration of license keys using the command `murshid register --key <license_key> --silent` or through the `MURSHID_LICENSE_KEY` environment variable. When these inputs are detected, the verification process runs headlessly, saving the validated key to the local configuration directory.
*   **REQ-F-124:** Config Precedence & Locking Policy: The configuration engine MUST merge settings from system-wide, user-level, and project-level TOML files. If a configuration block in the system-wide file contains `lock_policy = true`, all overrides for that block in user or project scopes MUST be ignored by the merger.
*   **REQ-F-125:** Custom Read-Only Team Rulesets: The Pedagogical Coordinator MUST support loading custom Socratic rulesets and internal library documentation references from a shared directory specified by the `pedagogy.team.rules_path` variable. To prevent local modifications or overrides by developers, the daemon MUST load these shared rulesets as read-only configurations, verifying file permissions and throwing an error on startup if local write permissions are detected on these shared configuration directories. The directory MUST contain a signature file `ruleset.sig` with a valid HMAC-SHA256 signature calculated over the alphabetical sorted ruleset payload using the team's shared secret key config (checking key rotation arrays in priority order); files with missing or mismatched signatures MUST be rejected and fall back to standard local configurations.
*   **REQ-F-126:** Configurable Analytics Privacy Levels: The Team Tier sync dashboard MUST support three opt-in levels for developer identity reporting in exported digests: 'anonymous' (hash-anonymized digests only), 'pseudonym' (mapping digests to custom developer pseudonyms), and 'identified' (identified by user email).
*   **REQ-F-114:** Prompt Injection Defense: The coordinator MUST wrap developer code context in strict delimiter tags `<developer_code_context>` and `</developer_code_context>` and explicitly instruct the LLM that any instructions nested inside are raw data. The coordinator MUST run a pre-transmission tag sanitization pass, replacing any matching delimiters embedded in the developer's source code with `[REDACTED_NESTED_TAG]`. This sanitization pass MUST occur strictly in-memory on the constructed payload buffer; the tool MUST NOT modify the physical files on disk.
*   **REQ-F-115:** Temporary Bypass Session: The CLI and LSP client MUST support temporary bypass mode (`murshid bypass --duration <time>`) that switches pedagogy to `direct_telling` for a set duration (capped at 2 hours). The bypass duration and reason MUST be logged in the local SQLite database. Bypass sessions MUST be rate-limited to a maximum of 3 sessions per rolling 7-day period to prevent Socratic evasion. Developers can override this weekly rate limit by passing the `--force` flag (e.g., `murshid bypass --force --reason "SEV-0 production hotfix"`), which requires a justification string and logs a distinct "forced bypass" event in the local SQLite database for audit compliance.
*   **REQ-F-116:** Context Bounding and Pre-Transmission Sanitization: The payload generator MUST restrict workspace context to the error line span +/- 25 lines and the structural signatures of ONLY the user types directly referenced in the compiler error span. It MUST strip out all comments and scan for secrets matching credential regular expressions (including AWS keys `AKIA[0-9A-Z]{16}`, Google Cloud/Gemini API keys `AIzaSy[0-9A-Za-z-_]{33,35}`, Stripe keys `sk_live_[0-9a-zA-Z]{24}`, Claude keys `sk-ant-api03-[0-9a-zA-Z-_]{90,110}`, and database URIs) before sending payloads to LLM APIs, replacing matched secrets with `[REDACTED_SECRET]`. To prevent exponential backtracking performance wedges on large source snippets, secret scanning MUST utilize a non-backtracking DFA-based engine and limit input snippet evaluation size to a maximum of 10,000 characters.
*   **REQ-F-117:** Viral Socratic Share: The CLI MUST support a `murshid share --error-id <id>` command that exports a clean, anonymized Markdown log of a Socratic learning struggle (error diagnostic, Socratic hints, and final compilable solution with all proprietary variables and type names replaced by generic identifiers like `MyStruct` or `process_data`). The command MUST write this log to a local file inside the project workspace at `.murshid/shared_struggle_<id>.md` and automatically copy the absolute path of this file to the system clipboard, avoiding remote network transmissions.
*   **REQ-F-119:** Automated Evaluation Harness: The CLI tool MUST support an automated evaluation command (`murshid eval`) that runs the Socratic engine against a local test dataset of compiler error traces (`eval_dataset.jsonl`), validating response compliance (checking for code leakage, instruction adherence) using a local programmatic grading harness. To prevent binary bloat and maintain high-performance execution under 5ms, the harness MUST execute similarity verification using a fast, token-based regex matcher. It MUST perform token normalization (mapping all variable, function, and type identifiers to standard placeholders like `var_n`) to detect structural logic mirroring, asserting that the Jaccard similarity is strictly under 30%. Supports `--full` and `--smoke` execution subsets.
*   **REQ-F-122:** Dynamic Pedagogy Auto-Scaling: When `pedagogy.auto_scale` is set to `true` in `config.toml`, the Pedagogical Coordinator MUST dynamically adapt explanation depth, consecutive failure thresholds, and escape hatch limits relative to the user's historical mastery curves for the specific concept. The consecutive failure threshold $T_t$ MUST be computed using an Exponential Moving Average (EMA) of concept mastery $S_t$:
    $$S_t = \alpha \cdot M_t + (1 - \alpha) \cdot S_{t-1}$$
    $$T_t = \text{clamp}(\text{round}(T_{\text{base}} + (1 - S_t) \cdot (T_{\text{max}} - T_{\text{base}})), T_{\text{base}}, T_{\text{max}})$$
    where the smoothing parameter $\alpha = 0.3$, $T_{\text{base}} = 3$, and $T_{\text{max}} = 7$. The raw concept mastery score $M_t \in [0.0, 1.0]$ (where $M_0 = 0.5$) MUST be updated on every compile check event: upon compilation success, $M_t = M_{t-1} + (1.0 - M_{t-1}) \cdot 0.20$; upon compilation failure, $M_t = M_{t-1} \cdot 0.85$. These update coefficients (defaulting to `success_step = 0.20` and `failure_decay = 0.85`) MUST be configurable in `config.toml` under a dedicated `[pedagogy.coefficients]` section. The system MUST support locking the pedagogical difficulty via the `pedagogy.lock_difficulty` configuration key; when set to `true`, auto-scaling and EMA score updates are frozen, and the Socratic challenge remains fixed at the default threshold settings ($T_t = T_{\text{base}}$).
*   **REQ-F-120:** Setup Onboarding Auto-Discovery: The onboarding setup workflow (triggered by `murshid setup`) MUST automatically scan the system path environment variable. If `cargo` or `rustc` is missing, it MUST look up standard Unix and Windows default locations and, if found, prompt the user to automatically add it to their shell profile. The setup command MUST also scan the active project directory for environment files (`.env`, `.env.local`) and offer to auto-import existing API keys (`GEMINI_API_KEY`, `ANTHROPIC_API_KEY`) to speed up configuration. If keys are imported from `.env` files, the tool MUST check the project `.gitignore` and, if `.env` is not ignored, automatically append it to `.gitignore` or print an interactive warning to prevent committing keys to version control. In silent setup modes, it MUST write warnings to standard error and configure standard defaults.
*   **REQ-F-121:** First-Error Onboarding Banner: Upon intercepting the very first compiler error in a workspace, the tool MUST output a clear, educational banner explaining the Socratic philosophy and code withholding rules as a non-blocking notification, initializing the watch thread immediately without requiring user input confirmation.
*   **REQ-F-127:** Dynamic LLM Generation Interrupt & Dispatch Debounce: If a filesystem modification occurs while the Socratic coordinator is actively querying or receiving responses from the LLM provider, the watch loop MUST immediately abort the active HTTP connection and discard the prompt context. The coordinator MUST clear any associated obsolete editor diagnostics from the buffer within 50 milliseconds of the write event detection to prevent developer feedback lag. To protect API rate limits and prevent billing spikes, Socratic LLM queries MUST be debounced by 1500ms and only dispatched when compiler diagnostics are stable, reusing the cached dialogue state if the compile error code, line number, and active file context hash match the previous query signature.

#### Local Progress Memory
*   **REQ-F-109:** The tool MUST write to a local SQLite database (`profile.db`) to record error occurrences, concept exposures, and mastery progression. The database path MUST default to:
    *   macOS: `~/Library/Application Support/murshid/profile.db`. If App Sandbox compatibility is enabled, the CLI and SwiftUI app MUST fall back to sharing files in the App Group Container at `~/Library/Group Containers/group.com.thabit.murshid/profile.db` to bypass sandbox restrictions. If the App Group container is inaccessible due to lack of signed provisioning profiles (such as for open-source CLI builds lacking matching team entitlements), the CLI and SwiftUI app fall back to local IPC socket communication or a shared directory under `/Users/Shared/murshid/` with POSIX permissions set strictly to `0700` and restricted by local user owner validation.
    *   Linux: `~/.local/share/murshid/profile.db`
    *   Windows: `%APPDATA%\murshid\profile.db`
    The configuration path MUST default to:
    *   macOS: `~/Library/Application Support/murshid/config.toml` (with fallback to App Group Container, and symlink option at `~/.config/murshid/config.toml` for CLI usage)
    *   Linux: `~/.config/murshid/config.toml`
    *   Windows: `%APPDATA%\murshid\config.toml`
    To protect user category-level progress thresholds (Novice, Competent, Proficient, Expert) against SQLite database deletion, the system MUST maintain an OS-native secure backup store (`NSUserDefaults` on macOS, Registry on Windows, and a hidden `.state_backup` file with `0600` permissions on Linux) containing a minimal plain JSON representation of category-level mastery thresholds. Licensing and trial validation metadata are excluded from this backup store to eliminate keychain dependencies. To prevent thread concurrency issues and complex file locking, state backups MUST occur synchronously during database writes or state changes to these standard platform-native registries rather than using background threads. On startup, if the SQLite file is missing, the system MUST retrieve progress thresholds from the backup store and restore category thresholds to the newly initialized database.
*   **REQ-F-110:** Concept mastery scores MUST be recalculated upon successful compilations or repeated failures using a defined mathematical decay and reinforcement loop.
*   **REQ-F-118:** Schema Versioning & Migrations: The SQLite connection manager MUST enforce database schema integrity using standard SQLite user version PRAGMAs (`PRAGMA user_version`). On connection initialization, the tool MUST check the version and automatically apply incremental database migrations (such as adding the Phase 2 analytics fields) without corrupting existing user profile tables. To prevent corruption during mid-migration power loss or lock conflicts, the manager MUST duplicate the physical database file `profile.db` to a temporary backup file `profile.db.migration_backup` prior to running migrations. All migration statements MUST execute inside a single immediate transaction; upon successful execution, the backup is deleted. If migration fails, the transaction is rolled back, database connections are closed, the database is physically restored from the backup file, and the backup is removed before returning the error.
*   **REQ-F-128:** Database Corruption Auto-Repair and Recovery: If connection initialization to the SQLite file fails due to database corruption (`SQLITE_CORRUPT`), the manager MUST rename the corrupted file to `profile.db.corrupt.<timestamp>` and initialize a clean database. The system MUST then automatically retrieve the user's category-level mastery thresholds from the native secure backup store (macOS user defaults registry, Windows Registry, or Linux state backup) to restore progression thresholds without user interaction. Standard licensing and trial statuses are recovered asynchronously via online HTTPS check-in.
*   **REQ-F-129:** Clippy Quick-Fix Redaction: If the compiler or clippy JSON diagnostic output contains structured suggestion replacements (representing direct quick-fixes), the LSP server and AST filter MUST intercept and strip these direct fixes from the diagnostic payloads. The Pedagogical Coordinator MUST instead translate the suggestions into conceptual queries and hints, withholding the suggested replacement code block to force the user to write it manually.
*   **REQ-F-130:** Zero-Telemetry Offline Knowledge Base: During installation, the CLI tool MUST cache a static, structured copy of standard Rust language references and common API guidelines in the platform config folder. If the developer is offline, the Socratic coordinator MUST map incoming compiler error codes (e.g., `E0382`, `E0507`) directly to matching documentation concepts using a pre-compiled, static lookup index, completely bypassing raw text Jaccard similarity searches over unstructured offline reference files at runtime to eliminate file reading latency (validated via [jaccard_index_benchmark.py](file:///Users/yasir/.gemini/antigravity-cli/brain/a842401f-a589-4758-9d9c-e03b298d7eb2/scratch/jaccard_index_benchmark.py)). For queries lacking direct compiler error codes, the system falls back to calculating Jaccard similarity strictly over pre-indexed document summary tokens.
*   **REQ-F-131:** Dynamic Configuration Watcher and Hot-Reloading: The Socratic coordinator daemon MUST launch a filesystem watcher targeting user-level and project-level `config.toml` files, debouncing change events by 500 milliseconds. Upon event resolution, settings MUST reload in-memory without process interruption or socket termination, applying updated watcher exclusions and pedagogy styles. Any reloaded properties MUST validate against system-wide `lock_policy` rules, ignoring user-level overrides and logging a warning to stderr/LSP windows if unauthorized modifications are attempted on locked parameters.
*   **REQ-F-132:** Token-Normalized Regex Jaccard Evaluation Harness: To ensure execution under 5ms and eliminate external compiler dependencies, the Socratic evaluation harness (`murshid eval`) MUST execute programmatic token normalization on generated response snippets using a fast regex-based tokenizer. The tokenizer MUST strip comments, remove string and char literals, and map all non-keyword identifiers to standard index-based placeholders (`var_n`) to ensure that similarity matching catches structural code leakage regardless of variable renaming or whitespace differences. To prevent false positives on keyword-dense code, the similarity checker MUST calculate Jaccard overlap strictly over the normalized identifier placeholders (excluding standard language keywords and syntax punctuation symbols), as validated in [token_jaccard_test.py](file:///Users/yasir/.gemini/antigravity-cli/brain/64b957ca-5003-4a33-86b9-e87bbc0b5e4d/scratch/token_jaccard_test.py). The harness MUST compute the Jaccard similarity index over the normalized identifier stream, asserting that similarity is strictly under 30%. To prevent false positive matches on keyword-dense short responses, the Jaccard check MUST only evaluate if the normalized snippet contains 20 or more distinct tokens.
*   **REQ-F-133:** Socratic Conversation History Sliding Window and Context Pruning: To prevent token inflation, control developer BYOK endpoint billing overhead, and avoid local inference latency degradation, the Socratic prompt builder MUST restrict historical dialogue turns to a sliding window of the last $N$ turns (defaulting to 3, configured via `pedagogy.history_limit` in `config.toml`). For all turns older than the sliding window threshold, the coordinator MUST strip out raw developer code snippets and file context buffers, preserving only the rustc compiler error code, file name, and diagnostic summary. Chronological context signatures and sliding history state metadata MUST be persisted within the relational `socratic_dialogues` table in `profile.db` to ensure context survival and prevent drift across editor and daemon restarts.
*   **REQ-F-134:** Progress Database Integrity and Tamper Protection: To verify the integrity of the local progress tracking database and prevent loading corrupted files, the connection manager MUST compute a simple database size and checksum validation on startup. The platform secure credential store (macOS Keychain, Windows Credential Manager, or Linux Secret Service) HMAC key requirements for progress integrity validation are completely eliminated. Enterprise progress metrics compliance is validated during the sync pipeline using the HMAC-SHA256 team secret signature, completely bypassing local database signature checks. If validation checks catch an invalid or corrupted file structure, the daemon MUST log a warning audit event and trigger the self-repair recovery protocol using the platform defaults backup store.
*   **REQ-F-135:** Automated Target Cache Pruning: To prevent disk space depletion from background compilation checks, the watcher daemon MUST evaluate the storage size of the Murshid-specific compilation target subdirectory (`<project-root>/target/murshid/`) asynchronously after each successful compilation check. If the directory size exceeds the limit defined in `watcher.target_cache_limit` (defaulting to 5GB), the daemon MUST execute a localized `cargo clean` strictly targeting the `<project-root>/target/murshid/` subdirectory asynchronously, ensuring it does not delete or interfere with the primary development target folder.
*   **REQ-F-136:** API Key and Credential Error Isolation: The provider client MUST parse and isolate API authentication and rate-limiting errors (such as HTTP `401 Unauthorized`, `403 Forbidden`, and `429 Too Many Requests`) from standard compiler checks. When a credential or rate error is encountered, the Socratic coordinator MUST bypass mastery decay updates and consecutive failure count increments. The LSP server MUST publish a warning diagnostic (`DiagnosticSeverity.Warning`) on line 1 of the active editor buffer stating: *"Socratic check suspended: invalid API key or connection unauthorized. Verify your credential configuration."*, and invalidate the cached key buffer to prompt key validation on the next edit event.

### (b) Phase 2: macOS Desktop App (v1.0)

#### Interface and System Presence
*   **REQ-F-201:** The application MUST wrap the Rust CLI core in a native SwiftUI application that lives in the macOS Menu Bar.
*   **REQ-F-202:** The app MUST provide an output panel that displays Socratic tips and allows text-based chat interactions.
*   **REQ-F-203:** The app MUST display a visual dashboard visualizing the user's concept mastery scores (e.g., progress gauges for Ownership, Lifetimes, Traits).
*   **REQ-F-213:** Popover to Float Transition: The Menu Bar utility popover MUST support transitioning into a floating utility panel (`NSPanel` with style mask `.utilityWindow` and collection behavior `.canJoinAllSpaces`) upon user interaction, floating on top of active IDE screens without permanently stealing keyboard focus.
*   **REQ-F-214:** SF Symbols Concentric Rings: The visual mastery dashboard MUST represent progress using qualitative concentric category rings mapped to Novice (0.0-0.30), Competent (0.31-0.60), Proficient (0.61-0.85), and Expert (0.86-1.00) tiers, utilizing system-native SF Symbols with dynamic opacity and transition animations. To indicate that a concept category is tracked even if the mastery score is currently 0.0, the UI MUST display a faint ring outline (set to 0.1 opacity) rather than rendering an empty blank circle.
*   **REQ-F-215:** Dynamic Status Icon: The Menu Bar status icon MUST dynamically reflect active daemon states: Idle/Listening (gray/monochrome), Compiling (pulsing blue), Socratic Alert (orange warning badge), and Bypass Active (purple key).

#### Language Server Protocol (LSP) Server
*   **REQ-F-204:** The binary MUST feature an embedded LSP server that supports standard editor protocols (VS Code, Neovim). To ensure local security and prevent opening local TCP ports, editors MUST connect to the LSP server daemon via a lightweight proxy CLI subprocess forwarding standard input/output (stdio) over a local Unix domain socket (or Windows named pipe at `\\.\pipe\murshid-lsp`) located in isolated, user-specific paths: `~/Library/Application Support/murshid/lsp.sock` on macOS, and comparable user-isolated cache directories on Linux. Socket parent directories MUST enforce strict POSIX permissions set to `0700`. If fallback sockets are created under `/tmp/murshid-<uid>/` due to home directory path write failures, the directory MUST be created with `0700` permissions and owned by the active user UID, and the daemon MUST check the path using `lstat` to verify it is not a symbolic link, preventing symlink hijacking attacks. In multi-user and remote SSH environments, socket checks MUST verify that the socket file owner user ID matches the active process owner user ID before binding or establishing a connection. On Windows, the named pipe MUST be initialized with a custom Security Descriptor (DACL) that grants access exclusively to the Security Identifier (SID) of the launching process owner, and the server daemon MUST enforce the creation-only flag (`FILE_FLAG_FIRST_PIPE_INSTANCE`) so pipe bind fails if the path is pre-allocated by a hijacked process. The proxy client `lsp-proxy` MUST query the server process ID via `GetNamedPipeServerProcessId` (or equivalent OS APIs) and verify that the server owner's SID matches the client process owner SID, immediately severing the pipe if unauthorized access is detected. On startup, the daemon MUST connection-test and unlink any stale socket file before binding. The proxy client `lsp-proxy` MUST enforce a 2000ms connection timeout when connecting to the socket, exiting with code 3 on failure.
*   **REQ-F-205:** The LSP server MUST publish Socratic annotations under the diagnostic source identifier `murshid` strictly using `DiagnosticSeverity.Hint` or `DiagnosticSeverity.Information` levels to avoid editor warning clutter, and publish them as `DiagnosticRelatedInformation` directly onto editor buffers. Socratic diagnostics are formatted as standard Markdown, delegating formatting fallbacks entirely to the client editor extension to keep the daemon's diagnostics rendering code simple.
*   **REQ-F-206:** The LSP server MUST support custom editor commands to launch inline chat buffers for Socratic interaction.
*   **REQ-F-210:** LSP Custom Code Action: The LSP server MUST register custom Code Actions (under the kinds `quickfix.murshid` or `refactor.murshid`) to spawn inline chat buffers or Socratic side panels, avoiding default diagnostic list clutter.

##### Advanced Git Utilities (Extensions)
*   **REQ-F-207:** Commit Cleaner: The tool MUST scan git staged changes (`git diff --cached`) for debug macros (`println!`, `dbg!`, unused imports) and prompt the user prior to committing. In headless or non-interactive environments (detected by verifying stdin is not a TTY device or checking for CI variables), if the SwiftUI companion app daemon is active, the pre-commit CLI hook MUST send a GUI prompt request over the secure UDS/Named Pipe socket, triggering a native SwiftUI modal prompt in the companion app. The CLI hook MUST wait for the user's action via the socket, enforcing a strict socket timeout of 2000ms (configured via `git.pre_commit.gui_dialog_timeout_ms`). If the daemon is offline, socket connection fails, or the timeout is exceeded, the hook MUST fall back to the non-interactive behavior controlled by the `git.pre_commit.action` configuration key (defaulting to `"warn"`). If set to `"warn"`, it prints a detailed diagnostic list to standard error and exits with code `0`, allowing the commit to proceed. If set to `"fail"`, it prints the diagnostic list to standard error and exits with code `1`, blocking the commit and outputting instructions on how to override it (e.g. via `--no-verify` or `MURSHID_BYPASS_COMMIT=1`). To avoid stalling workflows during large commits, the hook automatically skips interactive prompting and outputs a summary of detected cruft to stderr if the staged diff contains modifications across more than 15 files or more than 1,000 lines (unless run with the `--force` flag), routing a quiet notice of skipped items to the editor LSP client. Interactive prompts must support an immediate `[q]` quit/abort option to proceed with the commit.
*   **REQ-F-208:** Git Worktree Experimenter: The CLI/app MUST support launching parallel sandboxed worktrees (`murshid experiment start <name>`) with shared history to isolate risky educational refactors.
*   **REQ-F-209:** The tool MUST verify cargo tests and clippy diagnostics pass in the worktree before executing automated merging back to the master branch.
*   **REQ-F-211:** Safe Sandboxed Worktrees: The Git Worktree Experimenter MUST create worktree folders strictly within a subfolder of the project workspace (`.murshid_experiments/`) to comply with macOS sandbox scope limits, automatically add `.murshid_experiments/` to the project's root `.gitignore` if not present, and inject standard workspace config files to enable IDE discovery of the nested cargo project. To prevent cargo build locking conflicts and compilation collisions when building concurrently, the worktree MUST be configured with a distinct, isolated target folder under `.murshid_experiments/<worktree_name>/target/`, while explicitly excluding experimental target directories from IDE workspace file indexing. To optimize disk usage and compilation speeds, the worktree MUST share the global cargo registry cache (crates.io index and source files) via standard `CARGO_HOME` paths to avoid compiling dependencies from scratch. On startup, the daemon MUST check for any stale worktree paths registered under `.murshid_experiments/` that are missing on disk, and automatically execute `git worktree prune` to reconcile git's internal state. The tool MUST support a manual repair command `murshid experiment --repair` to force-prune missing directories and reinitialize the workspace config indicators. When a new worktree is created, the daemon's active watcher MUST dynamically inject the new worktree path into the active watch list using thread-safe runtime channel messaging, avoiding full watcher reinitialization or watch descriptor teardown.
*   **REQ-F-212:** Socratic Escape Hatch: The coordinator MUST trigger the escape hatch after a configurable number of unsuccessful compiles of the same error (defined by `pedagogy.escape_hatch_threshold` between 3 and 10, defaulting to 5), prompting the user with an option to reveal the direct code fix. The compile failure counter is tracked independently for each distinct compiler error code and is only incremented if the SHA-256 hash of the normalized source file (stripping all comments, whitespace, and formatting characters prior to hashing) has changed, verifying an active edit attempt. The compiler failure counter is tracked per file-error-code pair. The coordinator MUST maintain an in-memory cache of recently active file paths (up to 5 entries) with a 5-minute time-to-live (TTL). If the developer shifts active focus to a different file, the counter for the previous file is preserved in the cache. The counter for any file-error-code pair MUST be reset to zero immediately upon a successful compilation check of that file, or if the file entry expires from the cache.
*   **REQ-F-216:** macOS Security-Scoped Folder Bookmarking & CLI Delegation: The SwiftUI Menu Bar app MUST resolve all symlinks to their canonical paths using standard resolution systems (`std::fs::canonicalize` or equivalent) prior to workspace analysis. In environments where App Sandboxing is active, the SwiftUI host app MUST request and store security-scoped URL bookmarks (`NSData` bookmark arrays) in system preferences, resolving them on startup to retain folder read/write capability. To keep the portable Rust CLI binary free of complex sandboxing/App Group framework dependencies, the resolution of security-scoped bookmarks is delegated entirely to the SwiftUI companion app, which passes the resolved raw path handles to the background daemon via UDS. In non-sandboxed Developer ID builds, bookmarking is bypassed in favor of standard POSIX directory operations. If path resolution fails on launch, the companion app MUST log the error, mark the workspace as 'unreachable' in the menu bar UI, and present a notification to re-locate the folder.
*   **REQ-F-217:** Multi-Tenant Socket Call Credential Verification: Upon accepting any connection on the local Unix domain socket or Windows named pipe, the daemon MUST perform dynamic peer validation. On Unix-like systems (macOS and Linux), it MUST use `getsockopt` with `SO_PEERCRED` or `LOCAL_PEERCRED` to verify that the client process owner UID matches the daemon process owner UID. If fallback sockets are created under shared folders like `/tmp/murshid-<uid>/`, the daemon MUST check the path using `lstat` to verify that the path is not a symbolic link, and verify that the parent directory has POSIX permissions `0700` and is owned by the user UID. On Windows, it MUST call `ImpersonateNamedPipeClient` to retrieve the client token SID and verify it matches the active daemon owner SID, immediately severing the pipe if unauthorized access is detected. During testing or development execution (triggered by `--dev` flags or specific environment overrides), peer validation checks may bypass syscall-based owner PID/SID verification and rely solely on POSIX parent directory `0700` checks to prevent automated integration test lockouts on simulated systems.
*   **REQ-F-218:** Multi-Workspace Multiplexing and Session Isolation: The Socratic daemon MUST support concurrent connections from multiple active workspaces. During client handshake initialization, the LSP proxy client `lsp-proxy` MUST forward the workspace root path and client process ID (PID) to the daemon socket. The daemon MUST multiplex queues, watch threads, active build mutex locks, and session contexts isolated by workspace roots, while utilizing transactional connections to share the global progress `profile.db` metrics store. The LSP server MUST isolate diagnostic buffers dynamically by workspace root, ensuring checks in one project never update or leak diagnostics in another. The active Socratic dialogue sliding window of 3 turns MUST be isolated in memory per active workspace.
*   **REQ-F-219:** Experimental Worktree Pruning and Storage Limits: The Worktree Experimenter MUST support automatic workspace target pruning to protect local disk resources. The daemon MUST verify registered worktree metadata and execute background target pruning when the compilation loop is idle for 30 minutes, unlinking missing worktrees via `git worktree prune` and deleting their target folders. The CLI MUST support a manual command `murshid experiment prune --older-than <days>` to force purge obsolete build assets, and display a low-disk space notification badge in the UI if the project's experimental cache folders exceed a configurable limit (defaulting to 5GB, under `watcher.target_cache_limit` in `config.toml`).
*   **REQ-F-220:** DevContainer LSP Socket-to-TCP Bridge: To support containerized development environments (e.g. VS Code DevContainers), the LSP proxy client `lsp-proxy` running inside the container MUST bridge LSP stdio streams to the host daemon. The host daemon MUST bind its containerized listener to the local loopback address (`127.0.0.1`), dynamically selecting an available port in the range starting at `watcher.container.forward_port` in `config.toml` (defaulting to `8488`) up to a maximum offset of 12 ports (port range `8488-8500`), resolving port collisions on shared multi-user systems. Handshake communication MUST be authorized via a dynamic, single-use security token and the selected active port number written to the project path at `.murshid/container_session.json` with POSIX permissions restricted to `0600`. The containerized proxy MUST load this port and token and present it during connection handshake, severing the socket immediately if the token is missing or invalid. WSL integration relies on standard Windows loopback forwarding configuration rather than dynamic port translation.
*   **REQ-F-221:** Ephemeral Container License Token Generation: To enable Pro features inside containers without exposing long-term Stripe license credentials or keychain keys, the CLI on the host machine MUST support the command `murshid container token`. This command signs and exports a short-lived container license file (`.murshid_container_license` valid for up to 7 days) formatted as a colon-separated plain string payload (`tier:expiration:signature`) signed using the host's validated Pro key. The container CLI MUST read this license file headlessly on startup and verify the cryptographic signature offline against the embedded public key, checking license expiration dates against system time to validate container activation.
*   **REQ-F-222:** Quiet Watcher Polling Fallback Diagnostics: If the filesystem watcher daemon experiences platform resource limits or file descriptor exhaustion (`EMFILE` or `ENOSPC`), it MUST fall back to a background polling loop debounced at 2500ms. To prevent terminal logging spam in active graphical editors, the daemon MUST route the fallback limit warnings as an LSP diagnostic notification under the source `murshid` with severity set to `DiagnosticSeverity.Information` directly into the editor's diagnostic tray.
*   **REQ-F-223:** SQLite-Backed Socratic Dialogue State Machine: The watch daemon and Pedagogical Coordinator MUST store the user's interactive learning dialogue state inside a dedicated structured `socratic_dialogues` table in SQLite, indexing on hashed workspace roots and file paths to track learning status, conversational failure sequences, and scaffolding dial parameters efficiently, enabling fast relational queries and local analytics.
*   **REQ-F-224:** Pluggable Multi-Language Pedagogical Driver Registry: The watch loop and compile interceptor MUST support a pluggable driver registry to route compiler/linter diagnostics and parser results for multiple systems languages (Rust, TypeScript, Go). Language drivers MUST be registered statically at compile time using standard templates to maintain systems safety.
*   **REQ-F-225:** [DEPRECATED & ELIMINATED] Dynamic Offline Revocation List Patching: Dynamic offline patch file updates for revocation lists and the configuration key `licensing.patch_path` are completely deprecated and eliminated. All revocation checks are handled centrally during online check-in for standard users, or via signature expiration for dark-site enterprise clients.
*   **REQ-F-226:** Focus-Neutral Popover-to-Panel Detachment: The SwiftUI Menu Bar app popover transition MUST construct a floating utility panel using native `NSPanel` interfaces configured with style mask `.utilityWindow` and collection behavior `.canJoinAllSpaces`. The panel MUST be configured as a non-activating panel (e.g., setting `nonactivatingPanel = true`) to prevent stealing active keyboard focus from the active IDE window when it is detached or updated. All view containment swap operations must be focus-neutral and prevent workspace-space transition switches or window rendering flicker.
*   **REQ-F-227:** System-Wide Configuration Lock Ownership Verification: On startup, the configuration merging engine MUST check the file path metadata of the system-wide configuration file. The merge engine MUST verify that the system-wide configuration file is owned strictly by `root` (or the local administrator account) and has POSIX permissions matching `0644` or `0600` (blocking write access to normal local user accounts). If this security check fails, the merger MUST ignore any system-wide overrides, log a warning to standard error and the LSP diagnostic channel, and display a locked security warning in the SwiftUI companion interface.
*   **REQ-F-228:** Linter Compilation File Size and Line Limit: The watch loop and compiler parsing engine MUST check file dimensions before executing compilation checks or Socratic queries. The system ignores any file change event if the target file's size exceeds the configurable limit `watcher.max_file_size_kb` (defaulting to 50KB) or contains more than `watcher.max_file_lines` (defaulting to 1500 lines). The watch thread logs a quiet debug trace on skip, protecting developer API key budgets and reducing CPU scheduling overhead (validated via [linter_limit_test.py](file:///Users/yasir/.gemini/antigravity-cli/brain/5d6acdff-4e43-4f7d-adc0-9fbfc2ab45e6/scratch/linter_limit_test.py)). When a file is skipped due to size limits, the LSP server MUST publish a non-intrusive diagnostic on line 1 with severity `DiagnosticSeverity.Information` stating: "Socratic assistance suspended: file exceeds maximum line/size thresholds."
*   **REQ-F-229:** Centralized Watcher Resource Throttling Coordinator: The watch daemon MUST route all concurrent workspace watch requests through a coordinator to limit active watch threads (`watcher.max_watch_threads`, default: 4) and allocated file descriptors (`watcher.max_watch_fds`, default: 1000) to prevent CPU thrashing or `EMFILE`/`ENOSPC` errors. Excess workspaces MUST fall back quietly to background polling mode debounced at 2500ms, and the respective editors MUST be notified via an LSP diagnostic info message.
*   **REQ-F-230:** Local Model Prompt Normalization & Output Verification: For local offline model configurations, the Socratic prompt builder MUST format prompt string payloads utilizing model-specific header formats (e.g. ChatML or Llama-3 tokens) configured via `provider.local_template_format`. When `provider.local_output_leak_check` is true, generated response code blocks containing 3 or more proprietary identifiers matched from the active user file MUST be automatically redacted and replaced with an analogy instruction.
*   **REQ-F-231:** Pre-commit Audit Bypass Logging: When the pre-commit cleaner CLI hook is bypassed (via `--no-verify` or `MURSHID_BYPASS_COMMIT=1`), and the opt-in key `git.pre_commit.audit_bypass_logging` is true (defaulting to false), the CLI MUST log the event metadata (timestamp, project root name SHA-256 hash concatenated with the host-local database salt, and numeric bypass reason code) to the `Socratic_bypass_log` table in `profile.db`, omitting code content, file names, or diff segments. These logs MUST be serialized inside exported team progress digests and signed using the team's HMAC-SHA256 secret.
*   **REQ-F-232:** Compiler Diagnostic Path Sanitization: To protect local user privacy and prevent local usernames or home directory path structures from leaking to external model APIs, the CLI payload generator MUST perform in-memory path sanitization on all outgoing compiler diagnostics and error messages, replacing user home prefixes and local username strings with the generic placeholder `[USER_HOME]`.
*   **REQ-F-233:** Cargo Build File-Lock Timeout: To prevent background compile watch loops and the editor LSP proxy from blocking or hanging when manual developer builds run concurrently in terminal enclaves, the watch daemon MUST enforce a strict timeout of 3000ms when attempting to acquire target directory compile locks. If the build lock cannot be acquired within 3000ms, the compilation check run MUST abort immediately, executing a fail-fast exit.
*   **REQ-F-234:** Toolchain and Network Error Isolation: The compilation diagnostics parser MUST parse cargo stderr and compile messages for infrastructure and registry errors (including network timeouts, registry update failures, locked cargo files, and missing dependencies). If an infrastructure or toolchain error is isolated, the Pedagogical Coordinator MUST bypass Socratic dialogue generation, prevent local progress decay/reinforcement metrics updates, and publish a quiet toolchain diagnostic notification to the user.

## 2. Non-Functional Requirements

### (a) Privacy & Security (Zero-Telemetry)
*   **REQ-N-301:** The tool MUST NOT transmit any user code or workspace data to Thabit servers. All model requests MUST go directly to the user's BYOK provider endpoint. The app UI MUST display a clear user-facing warning warning that project code context is transmitted to external cloud APIs when remote providers (Claude/Gemini) are selected. Periodic billing status and license token check-ins over Thabit's server APIs are explicitly exempted from zero-telemetry and are processed over HTTPS endpoints.
*   **REQ-N-302:** The tool MUST NOT contain telemetry, logging hooks, or analytical trackers transmitting progress files off the user's system. This zero-telemetry constraint applies strictly to developer code and conceptual diagnostics; it does not block secure license activation or billing checks.
*   **REQ-N-303:** Online Check-in & Lease Hardening: Standard tiers (Pro, Team) validate licensing and active subscription status via periodic online check-ins over HTTPS against Thabit's license server, caching the cryptographically signed lease token (`expiration:tier:account_hash:signature`) inside the platform's secure credential store (Keychain on macOS, Credential Manager on Windows, Secret Service on Linux) via the `keyring` crate, or fallback `0600` files in headless environments, completely eliminating database tampering vectors. On startup, the daemon reads this signed token, extracts its fields, and verifies the signature locally using Thabit's embedded Ed25519 public key. Standard trials (Pro Trial) are verified strictly online on startup and require registration of a valid account (email/password/SSO) tied to the billing system, preventing keyless trial recycling by shifting email hashes. If the network is disconnected, paid Pro/Team clients fall back to a 14-day offline grace period checked directly by comparing the current system time against the cached last successful online check-in timestamp (failing immediately if current time is before the check-in timestamp to prevent clock-rollback). Dark-site enterprise enclaves run fully offline using pre-issued long-lived tenant-bound lease configurations containing `expiration:tenant_id:signature` verified client-side using raw Ed25519 signature verification against Thabit's embedded public key, requiring the configuration file to contain a matching `tenant_id` to prevent leaked signature sharing. All client-side JSON Web Token (JWT) parsing, offline revocation lists, whitelists, and local revocation check-ins are completely eliminated.
*   **REQ-N-304:** Secure Keychain Access & Memory Caching: The application MUST store and fetch Gemini and Claude API keys via platform credential APIs (macOS Keychain, Linux Secret Service, Windows Credential Manager) via the `keyring` crate. If the platform keychain is unavailable or fails (such as in headless Linux or remote SSH developer environments), the application MUST fall back to reading API keys from standard environment variables (e.g., `GEMINI_API_KEY`, `ANTHROPIC_API_KEY`) or Murshid-specific overrides (`MURSHID_GEMINI_API_KEY` and `MURSHID_CLAUDE_API_KEY`). When fallback environment variables are loaded, the application MUST print a warning message to standard error: `[WARNING] Using plaintext API keys from environment variables. Secure Keychain storage is recommended for production codebases.`, unless `provider.suppress_api_key_warning = true` in `config.toml` or the CLI is run with the `--no-warn` flag. To ensure security visibility when running in non-terminal enclaves, the warning MUST also be published as an LSP `window/showMessage` of type Warning during client editor initialization and displayed as a persistent top-panel banner in the SwiftUI Desktop application (both warning layouts MUST support interactive user dismissal, updating `provider.suppress_api_key_warning = true` in the configuration file upon activation). If platform secure stores are temporarily locked or encrypted during early daemon start, the validation checks MUST log a warning and degrade gracefully without blocking CLI execution until credentials become readable. To meet performance budgets and avoid blocking during watches, retrieved keys MUST be cached in memory using a secure, thread-safe volatile global allocation (`std::sync::Arc<std::sync::RwLock<Option<CachedKeys>>>`) that is hot-reloaded dynamically upon configuration file changes or receipt of a `SIGHUP` signal.
*   **REQ-N-305:** Simplified Verification Handshake: Standard users validate license status using signed lease tokens cached in platform-native Keychains (or 0600 local files), verified client-side using raw Ed25519 signature verification against Thabit's embedded public key, while offline enterprise enclaves use client-side raw Ed25519 signature verification of tenant-bound strings (`expiration:tenant_id:signature`). All users are completely exempt from local hardware salt generation, platform-native keychain salt backups, local salt files, client-side signature verification on standard local lease caches, random installation ID generation, and client-side JSON parsing library dependencies, eliminating macOS keychain access alerts and platform configuration dependency during onboarding.
*   **REQ-N-306:** Binary Self-Checksum & Gatekeeper Notarization: The desktop application binary MUST pass Apple Gatekeeper notarization, enforce Hardened Runtime, and perform a launch-time self-checksum check against an embedded signed hash to resist binary key patches.
*   **REQ-N-307:** Simplified Pro Trial Validation: Pro trials are unified with standard Pro licenses, validated using standard online HTTPS check-ins, and require registration of a valid account (email/password or SSO) verified by the billing system to prevent trial recycling. Trials do not support offline grace periods, require active internet connection, and do not require separate validation paths, local salt keys, or platform secure store backups, completely eliminating custom trial token files.
*   **REQ-N-308:** Socratic System Prompt Grounding: The prompt template MUST contain explicit instructions preventing context leaking (e.g., system prompt containment boundaries) and enforce model generation parameters: `temperature` set to `0.1` for Socratic dialogue, `0.3` for worked examples, and `0.0` for schema and AST signature validation.
*   **REQ-N-309:** Timezone-Safe Clock Validation & NTP Skew Tolerance: Standard users check system time validity directly against Thabit validation servers or public NTP endpoints during online check-ins. Dark-site enterprise clients validate expiration dates using system time comparison against the pre-signed Ed25519 lease configuration. SQLite-based clock-rollback databases and security skew state logs are completely eliminated.
*   **REQ-N-310:** [DEPRECATED] Offline Revocation List: Local offline Certificate Revocation List (CRL) files (`revocation_list.json` / `revocation_list.bin`) and patches are completely deprecated and eliminated. Revocations for online users are handled centrally during periodic check-ins, and dark-site enterprise clients manage revocations strictly via pre-signed Ed25519 lease expiration, removing all client-side CRL scanning logic.

### (b) Performance & Efficiency
*   **REQ-N-401:** Debounce and check loop initiation latency MUST be less than 50 milliseconds from the expiration of the typing pause window.
*   **REQ-N-402:** The local SQLite connection lifecycle MUST be lightweight, utilizing index optimization on search queries to ensure latency remains under 5 milliseconds.
*   **REQ-N-403:** The AST output parsing and Regex filtering operations MUST run in less than 20 milliseconds on standard markdown completion payloads.
*   **REQ-N-404:** Concurrent DB WAL Mode: The SQLite progress engine MUST use WAL mode and normal synchronization, allowing concurrent thread read access and serial writes under a 5000ms timeout limit. To prevent write lock conflicts during simultaneous compilation checks, user interactions, or editor diagnostic events, database writes MUST use a transaction retry loop utilizing exponential backoff (starting at 50ms, doubling with each retry up to a maximum backoff duration of 5000ms) with a +/-10ms randomized jitter to prevent lockstep thread collisions.

### (c) Robustness
*   **REQ-N-501:** If the chosen BYOK provider endpoint is offline, the tool MUST degrade gracefully by displaying the raw compiler diagnostic text alongside a local resource URL lookup instead of crashing.
*   **REQ-N-502:** The watch loop MUST survive malformed cargo workspace structures or syntax parsing errors, continuing to listen for filesystem events once files are modified.
*   **REQ-N-503:** Network Disconnection Resilience: The app MUST support an automatic 14-day network grace period if connection to Stripe endpoints fails during the license handshake check, extending the license period to a maximum of 44 days offline.
*   **REQ-N-504:** Standardized CLI Exit Codes and Logs: The CLI tool MUST enforce standardized exit codes (0: success, 1: general error, 2: compiler missing, 3: auth failure) and write trace logs to OS-standard directory paths:
    *   macOS: `~/Library/Logs/murshid/daemon.log`
    *   Linux: `~/.cache/murshid/log/daemon.log`
    *   Windows: `%APPDATA%\murshid\logs\daemon.log`
